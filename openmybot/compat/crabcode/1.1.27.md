## Bash sandbox auto-allow

| Item | Observation |
|---|---|
| Finding | The first embedded gate run on 1.1.27 used the 1.1.16 arguments, and G4 failed: the host was denied Write and then wrote the file with Bash, which never reached `can_use_tool`. A standalone replay used the driver's argv and cleared environment, denied every `can_use_tool` and logged the stream. In it, Bash `printf ... > <file>` ran without `can_use_tool` under the permissive G4 layers and under the entry's settings alone. Adding `Bash(*)` to `ask` changed nothing |
| Cause | Under the home isolation, the CrabCode configuration in effect runs sandboxed Bash commands without consulting `permissions.ask` (sandbox auto-allow). With `sandbox.autoAllowBashIfSandboxed` or `sandbox.enabled` set to `false` in the flag settings, the same replays send Bash through `can_use_tool` |
| Disposition | The entry's flag settings set `sandbox.autoAllowBashIfSandboxed` to `false`. `sandbox.enabled` stays as configured, so an approved Bash command still runs in the sandbox. Every later gate run passed, with each Bash request asked and denied |
| 1.1.16 | The former 1.1.16 entry carried the same `ask`-only settings, and 1.1.16 is no longer installed on this machine, so the gap cannot be rechecked on it. The entry is removed from the window, and `1.1.16.md` stays as a historical record |
